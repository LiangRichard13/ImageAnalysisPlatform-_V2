# 分析端实施方案（本 repo：FRAME 消费者 + RESULT 生产者 + 归档）

- 读者：分析端开发（我们自己，`F:\ImageAnalysisPlatform-_V2`）
- 协议权威文档：[SHM_PROTOCOL.md](SHM_PROTOCOL.md)
- 设计依据：`docs/superpowers/specs/2026-09-27-shm-realtime-pipeline-design.md`

## 1. 职责与数据流

分析端一肩三职：

```
FRAME ring ──事件唤醒+latest-wins──> SharedMemoryIngestThread ──memcpy──> 引擎推理(ndarray)
                                        │心跳 analyzer_heartbeat_ms
                                        ├─> RESULT ring 写结果 ──SetEvent──> 孪生端
                                        └─> 归档队列 ──后台编码──> download/anomaly_api/{input,output}
```

原始帧与结果两条 ring 解耦：推理慢（dinomaly 秒级）只拖慢结果链路，孪生端看原始帧不受影响。

## 2. 改动清单（A1–A8）

| # | 文件/模块 | 改动 |
|---|---|---|
| A1 | 新增 `utils/ipc/shm_ring.py` | 纯 ctypes 封装（零第三方依赖）：`CreateFileMappingW/OpenFileMappingW/MapViewOfFile/CreateEventW/SetEvent/ResetEvent/WaitForSingleObject` + CTRL/slot 结构体读写。导出 `FrameRingProducer` / `FrameRingConsumer` / `ResultRingProducer` / `ResultRingConsumer`；attach 校验 magic/version/slot 尺寸 |
| A2 | 新增 `SharedMemoryIngestThread(QThread)` | 事件唤醒（WFSO 50ms 超时，ctypes 调用释放 GIL）→ latest-wins 读帧 → memcpy 出（≈10ms）→ 调引擎 → 结果写 RESULT ring → 投递归档队列；每轮更新心跳 |
| A3 | `utils/rule_based_wrinkle.py` | 拆 `process_array(gray: np.ndarray) -> (pred_u8, heat_u8, metrics_dict)`；输入即 GRAY8（等价 `cv2.imread(..., IMREAD_GRAYSCALE)`）；现有 `process_to_dir` 改薄壳，文件模式行为不变 |
| A4 | `utils/dinomaly_engine.py` | 在已有 `process_pil_image` 上加 ndarray 进/出的直通包装；GRAY8→RGB 用 `np.repeat` 三通道扩展（内存完成，无编解码）；`process_to_dir` 不动 |
| A5 | `utils/anomaly_detection_client.py` | 新增 `process_from_array(gray, engine) -> (pred, heat, json_dict)`；路径式方法不动 |
| A6 | 新增归档 worker | 队列容量 16，满丢最旧+告警；按**现行目录结构**落盘：`input/{id}/{frame_id}.png + request.json`、`output/{id}.png / {id}_heatmap.png / {id}.json`；热力图 PNG 沿用 `cvt2heatmap`（JET 彩色），与历史产物颜色一致 |
| A7 | `anomaly_detection_tab.py` | shm 模式状态栏：实时链路在线/离线、最新 seq、丢帧计数；文件轮询面板置灰提示"由实时链路接管"；引擎选择复用 |

## 3. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| Phase 1 | A1 + 协议文档 + 单测 + 双进程基准脚本 | 单测全绿；1fps×32MB×30min 零损坏（CRC 抽查）、端到端 <50ms |
| Phase 2 | A2–A8 | 模拟生产者打帧：结果 ring ≤ 推理+50ms；`IPC_MODE=file` 回归全通过；归档目录 diff 与现状一致 |
| Phase 3 | `tools/shm_file_bridge.py`（监听 `ONLINE_PROCESSING_AD_DIR`，`ReadDirectoryChangesW`+200ms 兜底；持 `IAP_PRODUCER_MUTEX`；解码失败重试 3 次后丢弃告警；已入 ring 文件移 `.ingested/`） | IKapExpert 实际落图 → shm_inspect 读到帧 ≤2s；重复入 ring = 0 |

Phase 4（SDK 采集进程）归相机端团队，见[相机端接入指南](相机端接入指南.md)；我们只出 `tools/shm_inspect.py` 诊断工具（dump CTRL/心跳/丢帧、单帧导 PNG、CRC 抽查）。

## 4. 测试计划

1. **单元**（A1）：slot 读写、seq 完成语义、落后一圈覆盖检测、CRC、事件唤醒+兜底轮询、create-or-open 并发；
2. **集成压测**（Phase 1 基准脚本）：双进程 1fps×32MB×30min，CRC 全量抽查，`dropped_by_lag` 语义正确；
3. **回归**（Phase 2）：`IPC_MODE=file` 下批处理/单张/检查点行为全部不变（现有测试 + 手工路径核对）；
4. **注入**：归档线程暂停不影响实时链路；生产者心跳超时 10s UI 显示离线、恢复接管后无感续流。

## 5. 运维与回退

- 一键回退：`.env IPC_MODE=file` → 走现有 `BatchProcessingThread` 文件链路，代码零改动；
- 排障：`tools/shm_inspect.py` 看 `dropped_*` 计数与心跳定位是哪一端的问题；
- 已知风险：Defender 干预（页文件 backed 影响面小，异常时加排除）、GIL（WFSO/解码在线程池）、QImage 零拷贝对齐（GRAY8 行对齐=width，见孪生端指南 §4 的同款注意事项）。
